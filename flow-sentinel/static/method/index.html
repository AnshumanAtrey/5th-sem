How the detectorwas built

CICIoT2023 (Canadian Institute for Cybersecurity, 2023): 4,66,86,579 labelled network flows, 33 attacks in 7 families (DDoS, DoS, Mirai botnet, reconnaissance, spoofing, web attacks, brute force) plus benign traffic.

From raw capture to this page

  1. 1Load4,66,86,579 flows from the 169 CSV parts of CICIoT2023, captured in 2023 on a lab network of 105 real IoT devices.
  2. 2Sample fairlyEvery flow of the rare attacks, up to 12,000 of each big one, and 120,000 benign: 4,58,995 flows.
  3. 3Clean0 exact duplicates and 0 contradictory rows dropped before splitting, so no flow sits in both the training and the test set.
  4. 4Check for leaksOne column, IAT, gives the answer away (below). It is removed from every model.
  5. 5Lock the test setA stratified 75 / 25 split: 3,44,246 training flows, 1,14,749 test flows, 45 features each.
  6. 6PrepareFill gaps with the training median, take log(1 + x) to tame huge counts, standardise. Fitted on training flows only.
  7. 7Train and compareAll 11 classifiers from the syllabus, scored on recall, precision, F1, accuracy and the confusion matrix, then 5-fold cross-validation.
  8. 8DeployGradient boosting exported to JSON and run in your browser with the same maths; a test checks it matches sklearn on 300 flows.

The column that knew too much

A decision tree naming all 34 labels, given different columns. One column alone scores 87.7%, against 74.9% for all 45 real traffic features together. IAT is meant to be the gap between packets, but in this dataset it tracks when in the capture a flow was recorded, and each attack ran in its own time window. So it identifies the recording session, not the traffic. On a live network a new attack happens at a new time, so the model never gets to see IAT.

  • IAT alone (1 column)87.7%
  • traffic features without IAT (45)74.9%
  • everything (46)90.2%

Dropping it costs 12.8% of headline accuracy and buys a model that can work on traffic it was not recorded with.

The case study's six questions

Can machine learning tell normal and malicious traffic apart?
Yes. The deployed model catches 95.95% of attacks and flags 8.52% of normal flows on traffic it never saw.
Which network features matter most?
rst_count, urg_count, Number, flow_duration, Header_Length: shuffling them hurts the model most (permutation importance).
Which algorithm has the highest recall?
Bagging, 96.35%, missing 3,086 of the test attacks.
Which attack categories are hardest?
Reconnaissance and spoofing. The types missed most often: Recon-OSScan (33% missed), DNS_Spoofing (21% missed), Recon-PingSweep (17% missed), MITM-ArpSpoofing (15% missed). They send a few ordinary-looking packets, not a flood; the floods are almost always caught.
How does class imbalance affect the model?
Accuracy misleads: 73.7% of test flows are attacks, so "always intrusion" already scores that, and naive bayes reaches 99.9% precision while catching only 27.9% of attacks. Class weighting does not raise macro F1 (77.8% vs 77.7%); it moves recall to the rare families (brute force 47% → 71%, web 73% → 83%) at the cost of the big ones (DDoS 97% → 86%).
Can it detect previously unseen traffic?
Partly. Retrained without a family, it still catches 100.0% of Mirai but only 46.5% of Spoofing.

Limitations

  • Lab traffic from one IoT testbed. A different network needs re-testing, ideally on its own captures.
  • Each row summarises a window of packets, so the detector works on traffic summaries, not single packets.
  • False alarms: 8.5% of normal flows are flagged at the default threshold. Raising it trades catch rate for fewer alarms (the slider on the detector shows exactly how much).
  • The share of benign flows was set by our sampling. Real networks have far fewer attacks, which lowers precision for the same false-alarm rate.
  • Attack families never seen in training are only partly caught. An anomaly detector alongside would help.
  • One layer of defence, not a guarantee.
